## 1. Reset automation

### Recorded reset path

`reset_home.csv` was recorded with `log_teleop_telemetry.py`. It is not merely a static
home pose: it contains an operator-demonstrated reset path whose final pose is home.
Recovery uses the raw measured `pos.<motor>` columns, avoiding dependence on which
LeRobot calibration ID is active at runtime.

### Safety sequence

`recovery.py halt` reads present position, writes it back as the goal, and ensures torque
is enabled. It deliberately disconnects without disabling torque, so the arm holds rather
than continuing toward a stale goal or falling under gravity.

The reset entry sequence changed during hardware testing:

1. halt at present position;
2. move only `shoulder_lift` toward the recorded path's clearance pose;
3. keep every other joint fixed until measured lift position is within the clearance
   tolerance;
4. align the remaining joints while holding the lift fixed;
5. replay the recorded path at its captured timestamps;
6. reassert and hold the final home pose.

The first lift-first implementation was only time-gated. The shoulder is gravity-loaded
and had not always physically reached clearance before pan began. The gate now reads
`Present_Position`; pan cannot start until the lift is within the configured tolerance.
Failure to reach it within five seconds aborts before pan motion.

The initial 20-tick tolerance was too strict: one run stopped at target 1714, present
1743, only 29 ticks away. The default is now 500 raw ticks, still configurable with
`--lift-tolerance`.

### Soak status

`reset_soak.csv` contains five repeats (1585 rows, 52.8 s), not the required ten. It was
also captured before the final feedback-gated lift-first sequence. The routine is
implemented, but its exit criterion remains pending: run ten consecutive resets with the
current code, then immediately run `diagnose.py` and record shoulder temperature.

```bash
python research/telemetry/recovery.py reset --port /dev/ttyACM0 \
    --home research/telemetry/runs/reset_home.csv --repeat 10 \
    --log research/telemetry/runs/reset_soak.csv

python research/telemetry/diagnose.py --port /dev/ttyACM0
```

## 2. Common detector interface

### Contract

`detectors.py` emits one causal score per input frame. Every detector is normalized so
`score = 1.0` is its configured operating threshold. Each row carries common metadata:
run, source, frame index, timestamp, marker, run/frame labels, detector, score, threshold,
trigger state, warm-up/scorable state, and measured scoring latency.

Implemented rungs:

| detector | signal | decision |
|---|---|---|
| `duration` | elapsed time only | configurable time threshold; ranking baseline |
| `d0` | gripper current + commanded gripper motion | conditioned uncommanded current drop |
| `d0r` | measured arm current − predicted free-space current | p99 per-joint floor, 3-frame persistence |

The duration baseline is deliberately first-class. On these files it ranks surprisingly
well because the long collision recording makes elapsed time correlate with positive
frames. That is exactly the confound the baseline is meant to reveal; it must remain in
the eventual held-out comparison.

### D0 is genuinely online

`OnlineD0.update(t, gripper_current, gripper_goal)` is stateful and consumes one frame at
a time. Batch scoring calls this same interface sequentially, rather than calculating a
whole-file approximation. A regression test confirms it remains numerically identical to
the established causal Week 1 rule on `slip_a.csv`.

The command condition remains essential. A synthetic commanded release produces no
trigger; the same current collapse with a stationary command crosses threshold.

### D0r integration

D0r reuses the fitted `freespace.npz` model and its causal feature path. The first 25
frames remain explicitly unscorable. Its alert mask now requires three consecutive
frames at or above the p99 floor, matching the earlier conclusion that contact is
sustained while model error is often spiky.

The common interface reproduces the key Week 1 separation:

| run | peak score | trigger |
|---|---:|---|
| `pair1_clear` | 0.70× floor | no |
| `pair1_obstacle` | 3.27× floor | yes |
| `pair2_obstacle` | 3.88× floor | yes |
| `pair3_obstacle` | 28.36× floor | yes |

`clean_a` remains the known p99 false positive at 1.17×. The interface did not hide or
retune it.

## 3. Reporting semantics fixed before corpus collection

The first report implementation counted any trigger anywhere in a failed run as a true
detection. That is wrong: an unrelated gripper release can happen before a later
collision, and `slip_a` contains an unmarked first slip five seconds before the marked
second slip.

Event attribution now uses rising threshold crossings inside an explicit window, by
default 2.0 s before through 1.0 s after onset. A crossing outside that window is a false
alarm even if the rollout eventually fails. If a crossing is matched, later crossings
are ignored because closed-loop execution would already have halted; earlier crossings
remain false alarms.

The report produces:

- run-level and frame-level AUPRC;
- false alarms per clean run and clean-run trigger rate;
- overall, slip, and collision event-matched recall;
- median marker-relative lead time;
- fraction detected with the configured recovery-time budget;
- mean scoring latency per frame.

Week 1 values are smoke tests only. Markers include operator reaction delay, several files
are deliberately induced faults rather than autonomous rollouts, and the sample size is
too small for confidence intervals. In particular, do not report the old +5.11 s lead for
`slip_a`; event matching correctly associates the later crossing with the marked event.

## 4. D0+ causal features

The `features` command writes 225 columns per frame at the default 10-frame window:

- current, load, velocity, position, and voltage levels;
- first differences;
- causal trailing mean, standard deviation, minimum, and maximum;
- absolute velocity/load means;
- commanded position, commanded velocity, and trailing command range;
- low-velocity/high-current stall proxies;
- metadata, labels, warm-up state, and window size.

Feature construction accumulates arrays before creating the DataFrame, avoiding the
fragmentation warning and poor scaling of inserting ~200 columns one at a time.

Following error is deliberately absent. The Week 1 logger stores `goal_pos` normalized
but `pos` in raw ticks; subtracting them would create a meaningless feature. The eventual
LeRobot-dataset adapter may add following error only when both are placed in a common
calibrated unit.

Metadata and label columns travel with the feature parquet for joining and splitting.
They must be excluded from classifier input.

## 6. D0r trajectory-B evaluation pre-registered

The p99 operating point was selected after viewing trajectory-A results, so it cannot be
changed after seeing trajectory B. `D0R_HOLDOUT_PROTOCOL.md` locks the following before
collection: p99 floor, 10-frame causal residual smoothing, 25-frame warm-up, three-frame
persistence, light/moderate contact, and a joint other than `shoulder_pan`.

Primary success requires a sustained crossing on the physically contacted joint in
`pair4_obstacle`, with no crossing in the identical `pair4_clear` trajectory. A different
percentile may be shown only as explicitly post-hoc sensitivity analysis.

### Result recorded later the same day — failed specificity

Trajectory B was collected as 649 frames and replayed into command-identical clear and
obstacle runs containing five collision keypresses. The locked A model found a strong
obstacle response (21.67× p99), including large residuals on `shoulder_lift` and
`elbow_flex`, but the clear replay also produced six alert episodes and peaked at 4.32×
on `wrist_roll`. The pre-registered primary result therefore failed.

Four contacts had ≥150-tick matched position divergence. The third keypress did not and
must not be treated as a validated collision merely because it was marked. A B-fitted
secondary model separated pair4 but became false-positive on trajectory-A clear, pointing
to inadequate trajectory/session coverage. Temperatures differed by roughly 5–8 °C, but
trajectory and temperature changed together.

Full result: [`PAIR4_HOLDOUT_RESULT.md`](./PAIR4_HOLDOUT_RESULT.md). No percentile was
retuned on pair4.
